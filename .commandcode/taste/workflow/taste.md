# Workflow

- Prefers non-destructive rewrites: build the replacement in a parallel sibling location (e.g. `webui-next/` next to `webui/`) and leave the original untouched for rollback, rather than replacing or moving files in place. Confidence: 0.65
- Prefers phased, incremental delivery with each phase independently reviewable/releasable over a single big-bang rewrite. Confidence: 0.65
- When rewriting a UI or service, wants functional behavior, routes/URL contracts, and assets preserved unchanged — visual/stack changes should not alter them. Confidence: 0.6
- For large refactors, wants a written plan presented for approval — with key decisions surfaced as explicit choices — before any implementation starts, then executes it phase by phase. Confidence: 0.5
- Wants to manually preview/accept a deliverable in a running environment: after a build, asks for the actual services to be started (e.g. master + worker + web from `build/dist`) so they can click through the UI themselves, rather than relying only on automated tests or a green build. Also expects the dependent services a feature needs to be actually running/enabled rather than stubbed — e.g. explicitly told to start the transfer service so a transfer job could be submitted and observed end-to-end. Interactive defects surface through this click-through pass, so a green build/unit-test run is not accepted as proof that a UI change actually works in the browser. Confidence: 0.75
- Treats the agreed phased plan as a living checklist and periodically asks for what remains: expects the agent to re-derive outstanding work from the original plan and from an actual comparison against the legacy implementation (each item backed by a concrete check — route lists, i18n keys, greps — not a from-memory summary), instead of being told the migration is done. Confidence: 0.5
- Develops on macOS, so platform-unsupported components (e.g. fuse mounts) are expected to be omitted from local runs. Confidence: 0.55
- Declines browser-automation tooling (headless/browser-driving tools) as a verification step — the browser click-through is something he does himself. Expects changes to be validated with what the repo already has (type-check, unit tests, production build, code audit) plus a hand-written manual checklist of what to click, rather than adding a new automation dependency. Confidence: 0.6
- When a plan lists work by priority, expects the whole remaining list carried out (start at the first item, but do the rest too) instead of stopping after the top-priority one and asking again. Confidence: 0.5
- When reporting a defect in one spot, expects the whole class of problem audited and fixed everywhere it occurs ("所有涉及列表的地方都要考虑") — not a point fix at the reported place — and wants that audit re-run to confirm no occurrences remain. Confidence: 0.6
